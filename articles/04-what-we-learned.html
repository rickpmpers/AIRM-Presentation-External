04 · What we learned

Building this across three AI coding tools

The architecture for AIRM was designed across eleven source planning documents. What came after was a deliberate exercise in multi-agent engineering continuity: the build was handed sequentially between three distinct AI coding environments—Codex, Claude Code, and Google Antigravity (Gemini)—each reading the previous agent's written record, challenging assumptions, and building forward to complete the product.

1. Codex: the initial MVP and domain model

Codex took the initial planning documents and built the first operational version: the Go assessment container domain model, the evaluation catalog, and the FastAPI carrier receiver. It established the foundational separation between local assessment and carrier export, though it carried forward early design assumptions that had not yet been tested against adversarial boundaries.

2. Claude Code: catching the silent integration bug

Claude Code took over the repository and subjected it to rigorous integration testing. The most critical discovery of this phase was a silent schema bug: the carrier receiver's Pydantic allowlist had the hallucination vector spelled "hallucination" instead of the canonical "hallucination_ood". Because no receiver tests existed, every real carrier upload would have failed schema validation with an HTTP 422.

Claude Code fixed the mismatch, added a 17-test receiver suite, built SQLite persistence and audit log tests, created portal end-to-end tests, and added the planted-secret leakage regression test verifying that proprietary evidence cannot cross to the carrier. It also crystallized docs/DECISIONS.md, correcting math direction errors (inverting governance maturity before risk blending) and documenting architectural constraints.

3. Google Antigravity (Gemini): completing the product & proving the loop

Google Antigravity took the tested foundation and engineered the complete feature set:

  • Multi-Format Architecture Intake: Built a pure Go standard-library parser for ten document formats (.docx, .xlsx, .csv, .drawio, .mermaid, .pdf, etc.) with AST component detection, eliminating external LLM or cloud API dependencies.
  • Cryptographic Supply Chain Integrity: Designed and implemented dynamic package synthesis with HMAC-SHA256 signature blocks (SignatureBlock) and bit-for-bit client verification in Go (VerifySignature).
  • Closed-Loop Telemetry & Underwriting: Wired AWS CloudWatch metrics with in-memory credential containment, connected score-only exports to the carrier, and proved the complete automated loop resulting in dynamic underwriting rate adjustments.
  • Containerization & Security Hardening: Built production multi-stage Dockerfiles with unprivileged users, automated self-signed TLS/mTLS certificate generation, and secure multi-container compose specifications.
  • Multi-Tenant IC Cloud: Replaced single-tenant environment variables with an isolated SQLite tenant registry and a rate-limited admin UI/API deployed live at airm-ic.selfserved.ai and central.selfserved.ai/airm-ic/admin.
  • Actuarial Loss Engine: Implemented the isolated pricing/ package featuring FAIR Monte Carlo loss simulation and the 75/25 AI-exclusion gap blend with public proxy class data.
  • Governance Expansion & Tool Adapters: Expanded catalogs to NIST AI RMF Generative AI Profile, ISO 42001/42005/23894, and OWASP 2025; normalized tool evidence adapters (Promptfoo, DeepEval, Giskard, ART, AIF360, Evidently); and built the offensive testing program schema.
  • Carrier White-Label Distribution: Added the display-only branding layer (config.BrandingConfig, GET /api/branding) per Decision 16.

Key architectural lessons learned

  1. Dynamic packages require cryptographic supply-chain verification: You cannot predict telemetry environments in advance, but you can never trust arbitrary code downloads. HMAC-SHA256 manifest signatures and local customer authorization are mandatory.
  2. Credentials must stay in volatile memory: Telemetry credentials (AWS, Datadog) must live exclusively in container memory and never touch disk, logs, or exports.
  3. Missing evidence must stay unknown: In risk modeling, unmeasured controls must never default to passing or a midpoint. Missing data lowers coverage, preserving truth.
  4. Durable written records enable zero-loss multi-agent handoffs: Systematic documentation (PROJECT_STATUS.md, DECISIONS.md, and shared Obsidian knowledge vaults) allowed three different AI harnesses to build a complex distributed system without regressions or stranded knowledge.
