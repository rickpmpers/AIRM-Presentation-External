02 · The architecture

A perimeter that actually holds

The hardest part of building a third-party AI risk assessment isn't the scoring — it's that no serious engineering org will let an outside tool see their source code, their cloud credentials, or their internal architecture. AIRM is architected so that raw data, proprietary architecture, and credentials never cross the company perimeter, while still enabling continuous, verified telemetry underwriting.

The two execution boundaries

AIRM operates across two strictly isolated boundaries:

  • The Company Assessment Container (Aglet Container): Deployed inside the customer's infrastructure (Docker, local workstation, or cloud VPC). It ingests system architecture specifications, requests and cryptographically verifies environment-specific telemetry packages, runs collectors locally using in-memory credentials, screens controls, and maintains a local SQLite audit trail.
  • The Carrier Central Authority (IC Cloud): Acts as the package synthesis authority and underwriting receiver. It dynamically synthesizes custom telemetry packages, signs them cryptographically, and receives only allowlisted, sanitized risk scores to calculate dynamic premium adjustments.

1. Multi-format architecture intake

Before an assessment runs, the container must understand what systems exist. AIRM includes a pure standard-library document intake engine that parses ten distinct formats without relying on heavy third-party services or external LLM APIs:

Supported inputs include .docx, .xlsx, .csv, .drawio / .xml diagrams, .mermaid / .mmd flowcharts, .pdf, .txt, .md, .json, and .yaml. The AST/text analyzer detects cloud and AI building blocks—such as Amazon Bedrock, Amazon SageMaker, AWS Lambda, Amazon S3, Vector Databases, and API Gateways—and maps each component directly to corresponding risk vectors and required telemetry packages.

2. Dynamic package synthesis & HMAC-SHA256 code signing

Because production environments differ wildly, pre-baking every possible monitoring agent into the customer container would bloat the deployment and create attack surface. Instead, IC Cloud dynamically synthesizes tailored telemetry packages based on the detected architecture and engineer directives.

To protect the client container from malicious or tampered code downloads, every package bundle synthesized by IC Cloud includes an immutable SignatureBlock containing an HMAC-SHA256 digest calculated over the canonical JSON manifest. Before the local container touches or stages any package, it verifies the signature bit-for-bit against the trusted authority key. If the signature doesn't match or the authority is unverified, the package is immediately rejected.

3. Local in-memory credentials & zero credential egress

Telemetry collectors (e.g. AWS CloudWatch, Datadog) require credentials. In AIRM, those credentials (e.g. AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY) are passed directly to the local container and held strictly in volatile process memory. They are never written to disk, never included in logs, and structurally cannot cross the network boundary to IC Cloud.

4. The score-only carrier export boundary

The carrier receiver accepts only a strictly allowlisted payload: 

{
  "schema_version": "v1.0",
  "assessment_id": "9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d",
  "company_id": "company-a",
  "combined_risk_score": 38.5,
  "technical_scores": {
    "uncontrolled_internet_access": 45,
    "hallucination_ood": 32,
    "model_drift": 28,
    "prompt_injection": 22
  },
  "governance_scores": {
    "nist_ai_rmf": 68,
    "iso_42001": 74,
    "owasp_llm_top_10": 80
  }
}

A dedicated regression test plants synthetic secrets, local file paths, internal reviewer names, and stderr diagnostics into the local store and asserts that none can appear in the carrier payload. Allowlisting first means there's no field you forgot to sanitize; only uncalibrated numeric scores and framework metadata are permitted to leave.

5. Closed-loop underwriting rate adjustment

AIRM proves the complete closed loop from architecture intake to policyholder rate adjustment:

  1. Architecture document uploaded and parsed locally into component specifications.
  2. Container requests dynamic telemetry packages with optional engineer directives.
  3. IC Cloud synthesizes and cryptographically signs packages with HMAC-SHA256 digests.
  4. Container verifies signatures bit-for-bit and prompts for customer authorization.
  5. Container executes verified collector locally using in-memory AWS credentials.
  6. Control screening completes and exports sanitized scores to IC Cloud.
  7. IC Cloud receives the score, compares it to historical baseline submissions, and computes a dynamic underwriting rate adjustment (e.g. -2.5% premium adjustment).

6. Multi-tenant IC Cloud & carrier white-label distribution

IC Cloud provides true multi-tenant isolation: a per-tenant SQLite registry enforces independent token digests, signing keys, and assessment records. It features a rate-limited administration surface (/admin/api/* and web UI at /admin) protected by sliding-window rate limiters and automatic lockout mechanisms.

Furthermore, under Decision 16, the customer-facing container includes a configurable white-label branding layer (config.BrandingConfig, exposed via GET /api/branding). This allows insurance carriers to distribute the verified assessment container directly to their policyholders under the carrier's own product name, logo, and theme—without modifying the underlying cryptographic, scoring, or privacy boundaries.

Fail-safe direction: missing evidence stays unknown

If a connector is unconfigured or a scan fails, the system does not invent a passing score or fabricate a midpoint. Missing evidence is explicitly classified as unknown, lowering overall assessment coverage. In insurance and risk modeling, silence is evidence of absence, not evidence of safety.
